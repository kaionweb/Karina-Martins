## Scope Note (decisões registradas nesta preparação)

1. **Story fora do PRD original, Epic 10 (mesmo padrão informal dos Epics 6-9 — sem documento de epic formal).** Quarta story do Epic 10, mas não faz parte do fatiamento original de "Home real" (Stories 10.1-10.3, todas `Done`) — é um bug de sessão encontrado durante o smoke test manual dessas stories: reload de página em qualquer rota do grupo `(app)` derruba o usuário para `/select-profile` mesmo com login válido, porque só o access token em memória (15 min, perdido a cada reload) carrega `profileId`; o refresh token (cookie httpOnly, 7 dias) nunca carregou esse campo desde a Story 1.2.
2. **Causa raiz confirmada em código (não hipótese):** `AuthService.issueTokens`/`AuthService.refresh` (`apps/api/src/modules/auth/auth.service.ts`) assinam/verificam o refresh token inline via `jwt.sign`/`jwt.verify` + um método privado `refreshSecret()`, sempre com payload `{ sub }` — nunca `profileId`. `ProfilesService.selectProfile` (`apps/api/src/modules/profiles/profiles.service.ts`) só reemite o **access token** (`signAccessToken({ sub, profileId }, ...)`); o cookie de refresh emitido no login original permanece intocado. No frontend, `useAuthGuard` (`apps/web/src/hooks/useAuthGuard.ts`, usado por `apps/web/src/app/(app)/layout.tsx` — toda a área logada — e mais 4 páginas: `dashboard/page.tsx`, `dashboard/transcripts/[profileId]/page.tsx`, `catalog/[showId]/page.tsx`, `lesson/[lessonId]/page.tsx`) redireciona para `/select-profile` sempre que `options.requireProfile` é true e `useProfileStore.activeProfile` (Zustand, 100% em memória, sem persistência) está `null` — o que é sempre o caso logo após um reload, mesmo que `getAccessToken()`/`POST /auth/refresh` tenha recuperado a sessão com sucesso.
3. **Correção em duas pontas, decidida com o usuário (não renegociar):** (a) backend passa a carregar `profileId` também no refresh token, reemitido a cada seleção de perfil, e `POST /auth/refresh` passa a devolver esse `profileId` explicitamente no corpo JSON da resposta (nunca decodificado no cliente — `apps/web/src/lib/auth/index.ts` já segue esse padrão de nunca decodificar JWT no front); (b) `useAuthGuard` passa a usar esse `profileId` (quando presente) como um "hint" para repopular `useProfileStore` via `listProfiles()` antes de decidir redirecionar.
4. **Compatibilidade retroativa é requisito explícito, não nice-to-have:** um refresh token já emitido antes desta mudança (payload `{ sub }`, sem `profileId`) precisa continuar sendo aceito por `POST /auth/refresh` sem erro — o comportamento nesse caso é idêntico ao atual (usuário cai em `/select-profile`, não é deslogado à força). Teste explícito de compatibilidade retroativa é obrigatório (ver Testing).
5. **Segurança do cookie não muda** — só um campo a mais no payload já assinado (`profileId?: string`), reaproveitando a mesma interface `AccessTokenPayload` (`apps/api/src/common/auth/jwt.util.ts`) já usada pelo access token, que já tem esse campo opcional. Continua `httpOnly`, `secure`, `sameSite: "none"`, `path: "/auth"`, ilegível por JS no browser.
6. **[AUTO-DECISION]** A forma exata de expor o "hint" de `profileId` do refresh para o `useAuthGuard`, deixada em aberto pelo pedido original, é: um par getter/setter novo em `apps/web/src/lib/auth/token-store.ts` (`getProfileIdHint`/`setProfileIdHint`, módulo-level, mesmo padrão de `getStoredAccessToken`/`setStoredAccessToken` já existentes ali), populado dentro de `refreshAccessToken()` em `apps/web/src/lib/auth/index.ts` a partir de `data.profileId` da resposta de `/auth/refresh` **(reason: `token-store.ts` já é o único módulo de estado em memória de auth no frontend, sem dependência de Zustand — manter o hint lá, ao lado do access token, preserva a separação de camadas já estabelecida no projeto: `lib/auth` nunca importa a store, quem orquestra popular `useProfileStore` é o hook consumidor, `useAuthGuard`, não a lib)**.
7. **[AUTO-DECISION]** O hint é consumido (não persistido indefinidamente): assim que `useAuthGuard` usa o `profileId` do hint para achar e popular um perfil via `listProfiles()` — com sucesso ou não — ele é limpo (`setProfileIdHint(null)`) **(reason: o hint só precisa sobreviver do momento do refresh até a primeira checagem do guard logo depois; mantê-lo indefinidamente em memória não tem utilidade adicional e evita reprocessar `listProfiles()` de novo a cada remount do guard nas rotas subsequentes da mesma sessão, algo que a store `activeProfile` já resolvida cobre)**.
8. **Efeito colateral aceito e documentado (não é bug):** trocar de perfil agora também renova a janela de 7 dias do cookie de refresh (reemitido a cada `/select`). Comportamento aceitável — atividade estende sessão, mesma decisão já tomada com o usuário.
9. **SEC-002 (Story 1.4) não muda:** a validação que bloqueia um perfil `CHILD` ativo de trocar para outro perfil em `ProfilesService.selectProfile` continua exatamente igual e é executada **antes** de qualquer reemissão de cookie — só o caminho de sucesso (perfil elegível, validação já passada) ganha a reemissão do refresh token.

## Story

**As a** usuário logado com um perfil já selecionado,
**I want** que minha sessão (login + perfil ativo) sobreviva a um reload de página,
**so that** eu não seja jogado de volta para a tela de seleção de perfil toda vez que atualizo o navegador, mesmo com uma sessão válida.

## Acceptance Criteria

1. `apps/api/src/common/auth/jwt.util.ts` ganha `signRefreshToken(payload: AccessTokenPayload, expiresIn: ExpiresIn): string` e `verifyRefreshToken(token: string): AccessTokenPayload`, usando `process.env.JWT_REFRESH_SECRET`, seguindo exatamente o mesmo formato de `signAccessToken`/`verifyAccessToken` (mesma interface `AccessTokenPayload`, `{ sub, profileId? }`).
2. `REFRESH_COOKIE`/`REFRESH_COOKIE_OPTIONS`, hoje constantes privadas de `auth.controller.ts`, são extraídas para um módulo compartilhado em `apps/api/src/common/auth/` (junto de uma constante `REFRESH_TOKEN_EXPIRES_IN = "7d"` também extraída, hoje privada em `auth.service.ts`), para que `profiles.controller.ts`/`profiles.service.ts` também possam usá-las sem duplicação.
3. `AuthService.issueTokens`/`AuthService.refresh` passam a usar `signRefreshToken`/`verifyRefreshToken` do `jwt.util.ts` em vez de `jwt.sign`/`jwt.verify` inline; o método privado `refreshSecret()` é removido. Login e refresh continuam funcionando exatamente como hoje para um usuário sem perfil selecionado (nenhuma mudança de comportamento observável neste refactor isolado).
4. `POST /profiles/:id/select` (`ProfilesController.select`/`ProfilesService.selectProfile`), no caminho de sucesso (após a checagem SEC-002 já ter passado), passa a reemitir — além do access token que já retorna hoje no corpo — um novo cookie de refresh token (`Set-Cookie`, mesmas opções: `httpOnly`, `secure`, `sameSite: "none"`, `path: "/auth"`) contendo `{ sub, profileId: targetProfileId }`. O corpo da resposta continua `{ accessToken }`, sem mudança de contrato.
5. `AuthService.refresh()` decodifica o refresh token recebido via `verifyRefreshToken` e retorna `{ accessToken, profileId }` no corpo JSON — o novo access token emitido carrega o mesmo `profileId` (quando presente) do payload do refresh token; `profileId` fica `undefined` na resposta quando o refresh token (novo ou legado) não contém esse campo.
6. Um refresh token emitido **antes** desta mudança (payload `{ sub }` apenas, sem `profileId`) continua sendo aceito por `POST /auth/refresh` sem erro: `verifyRefreshToken` decodifica normalmente, a resposta é `{ accessToken }` (sem `profileId`), sem 401/500 indevido — compatibilidade retroativa explícita.
7. A validação SEC-002 (Story 1.4: perfil `CHILD` ativo não pode trocar para outro perfil via `/select`) continua bloqueando exatamente os mesmos casos que bloqueia hoje, sem regressão — a reemissão do cookie de refresh não altera nem contorna essa checagem.
8. Frontend: `apps/web/src/lib/auth/token-store.ts` ganha `getProfileIdHint()`/`setProfileIdHint(profileId: string | null)` (módulo-level, mesmo padrão de `getStoredAccessToken`/`setStoredAccessToken`); `refreshAccessToken()` em `apps/web/src/lib/auth/index.ts` popula esse hint com `data.profileId` (ou `null` se ausente) a cada refresh bem-sucedido. `lib/auth` continua sem importar `useProfileStore`/Zustand.
9. `useAuthGuard` (`options.requireProfile: true`): quando `getAccessToken()` resolve com sucesso, `useProfileStore.activeProfile` está `null`, e `getProfileIdHint()` retorna um id não nulo, o hook chama `listProfiles()` (`@/lib/api/profiles`) e procura o perfil correspondente na lista retornada. Se encontrado, chama `setActiveProfile` com esse perfil **antes** de decidir o redirect (fica `ready: true`, sem navegar para `/select-profile`). Se não encontrado (ex.: perfil deletado nesse meio tempo) ou se não houver hint, o comportamento atual é preservado (redireciona para `/select-profile`). Em qualquer um dos dois casos, o hint é consumido (`setProfileIdHint(null)`) após a tentativa.
10. `pnpm build` completo do monorepo passa sem erros.

### API Specification

- `POST /auth/login` (`AuthController.login`) → `200 { accessToken }` + `Set-Cookie: refresh_token=...` (payload `{ sub }`, sem `profileId` — usuário ainda não selecionou perfil neste ponto). Contrato inalterado.

- `POST /profiles/:id/select` (`ProfilesController.select`, `JwtAuthGuard`) → `200 { accessToken }` (corpo inalterado) + **novo:** `Set-Cookie: refresh_token=...` (payload `{ sub, profileId: targetProfileId }`). `404 PROFILE_NOT_FOUND`; `403 FORBIDDEN` (SEC-002) — inalterados.
- `POST /auth/logout` — inalterado (`res.clearCookie`, mesma constante de nome de cookie, agora importada de `refresh-cookie.ts`).
