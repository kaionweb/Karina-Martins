## Scope Note (decisões registradas nesta preparação)

1. **Escopo restrito ao catálogo, conforme a AC desta story — não ao seed completo.** O `CLAUDE.md` (seção "SEEDS DE DEMONSTRAÇÃO") descreve um seed final com conta familiar, conta adulta, badges e XpEvents — mas isso é responsabilidade da **Story 5.3 "Seed de demonstração completo"** (Epic 5), cujo próprio título indica que é o seed final e completo. Os models `Badge`/`XpEvent` nem existem ainda (Epic 3). Esta story cria **apenas** a parte de catálogo (2 shows, 1 trilha e 5 lições cada) pedida literalmente pela AC1/AC2 do Epic 2 — o seed será estendido incrementalmente pelas próprias stories dos Epics 3/4/5 conforme os models forem existindo, terminando na 5.3.
2. **`seed.ts` roda via `tsx`, não via `node` direto nem `ts-node`.** Rodar `.ts` direto com `node` (suporte nativo a TypeScript do Node 24) foi exatamente a causa do bug ARCH/infra corrigido nas Stories 2.2/2.3 (`ERR_MODULE_NOT_FOUND` em imports relativos sem extensão) — `tsx` evita isso completamente por não depender da resolução de módulos nativa do Node para arquivos `.ts`. `ts-node` foi considerado e descartado por ser mais lento e exigir mais configuração para ESM/CJS neste monorepo.
3. **`seed.ts` NÃO deve ser adicionado ao `include` de `packages/database/tsconfig.json`.** Isso mudaria o `rootDir` inferido pelo `tsc` (usado pelo script `build`) de `src/` para a raiz do pacote, e os arquivos compilados passariam a sair em `dist/src/index.js` em vez de `dist/index.js` — quebrando `main: "dist/index.js"` em `package.json`, que `apps/api`/`apps/web` dependem para resolver `@ipp/database` (a mesma classe de bug de resolução de módulo corrigida nas Stories 2.2/2.3). `tsx` compila em memória na hora de rodar, sem tocar em `dist/`.
4. **Idempotência:** `seed.ts` deve poder ser rodado múltiplas vezes sem erro (AC2 diz "roda sem erro", e a demo pode precisar ser re-populada mais de uma vez antes da apresentação ao cliente). Como `title` não é `@unique` no schema (só `id` é), a estratégia é `deleteMany` pelos títulos conhecidos dos 2 shows do seed antes de recriar — o cascade delete já testado na Story 2.1 (`Show → Track → Lesson`) limpa tudo de baixo pra cima automaticamente.

### Data Models

Nenhum model novo — usa `Show`/`Track`/`Lesson` já existentes desde a Story 2.1. [Source: packages/database/prisma/schema.prisma]

```prisma
model Show {
  id           String   @id @default(cuid())
  title        String
  synopsis     String   @db.Text
  thumbnailKey String
  tracks       Track[]
  createdAt    DateTime @default(now())
}

model Track {
  id      String   @id @default(cuid())
  showId  String
  title   String
  order   Int
  lessons Lesson[]
}

model Lesson {
  id          String   @id @default(cuid())
  trackId     String
  title       String
  order       Int
  contentBody String   @db.Text
  createdAt   DateTime @default(now())
}
```

### Regra de domínio (obrigatória)

[Source: CLAUDE.md#REGRAS DE DOMÍNIO]

> Catálogo: apenas metadados factuais de obras + conteúdo 100% original. PROIBIDO: imagens/nomes de arquivos de personagens ou pôsteres de terceiros, legendas transcritas, letras de música. Thumbnails = artes próprias do design system.

Os 2 shows, sinopses e o `contentBody` das 10 lições devem ser conteúdo original criado para este produto — não nomes, personagens ou texto de nenhuma obra de terceiros existente. `thumbnailKey` é só um identificador de string (mesmo padrão da Story 2.1/2.2 — não é upload nem URL de imagem).
