## Scope Note (decisões registradas nesta preparação)

1. **Módulo chamado `parent` (não `parent-dashboard`/`ai-tutor` literal do texto prosa de `architecture.md`)** — a arquitetura descreve o módulo como "Parent Dashboard Module", mas todos os módulos já implementados usam nomes de pasta curtos, de uma palavra (`lessons`, `catalog`, `gamification`, `profiles`, `ai`) — mesma divergência consciente já aceita nas Stories 2.3/4.1 entre a prosa da arquitetura e a estrutura real de pastas. Endpoint continua exatamente `/parent/profiles/:id/journey`, conforme a REST spec.
2. **Endpoint restrito a perfis ADULT — perfil ativo CHILD recebe 403.** Nenhuma AC desta story exige isso literalmente, mas é a mesma precaução de segurança já estabelecida no próprio código (`ProfilesService.listForUser`, Story 1.4: perfil CHILD ativo não pode listar/acessar dados de outros perfis da conta) e alinhada ao espírito geral do `CLAUDE.md` de proteção de dados de perfis CHILD. Reaproveita `ProfilesService.isChildProfile` (Story 4.4) para essa checagem — sem duplicar lógica de acesso a `Profile`.
3. **Perfil-alvo (`:id`) precisa pertencer à mesma conta do usuário autenticado E ser do tipo CHILD — senão 404, sem diferenciar "não existe" de "existe mas não é seu/não é CHILD".** Mesmo racional de segurança já documentado em `ProfilesService.selectProfile` (Story 1.4, comentário SEC-002): não confirmar a validade de um ID de perfil para quem não tem acesso a ele.
4. **Reaproveita `GamificationService.getXpTotal`/`getBadges` (Stories 3.2/3.4) para XP e badges — nenhuma lógica de agregação duplicada.** Ambos os métodos já recebem `profileId` como parâmetro (não derivam do perfil ativo internamente), então funcionam diretamente para um perfil-alvo arbitrário, exatamente como esta story precisa.
5. **"Lições concluídas" é uma lista (não só uma contagem)** — a Story em si diz "quero ver o progresso da minha criança (lições concluídas, XP, streak, badges)", e uma lista com título+data permite ao responsável de fato acompanhar o que foi estudado, mais útil que um número isolado. Nenhuma agregação desse tipo existe ainda — implementada nesta story a partir de `LessonProgress` (já existe desde a Story 2.3), sem model novo.
6. **Frontend: página `/dashboard` (Client Component), mesmo padrão já usado desde a Story 2.3/3.2/3.4** — como ainda não existe UI de login/seleção de perfil (decisão consciente da Story 1.4, ainda não revisitada), a verificação end-to-end real desta story também depende de injeção manual de token via console do navegador, mesma limitação já aceita nas stories anteriores de `apps/web`. A página busca `GET /profiles` (primeiro consumidor de frontend desse endpoint, existente desde a Story 1.4 mas nunca consumido pela web) para encontrar o(s) perfil(is) CHILD da conta, e para cada um busca `GET /parent/profiles/:id/journey`.
7. **Reaproveita `XpBar`/`BadgeGrid` (Stories 3.2/3.4) e o schema `Badge` (`packages/shared`) sem alteração** — evita duplicar componentes/tipos já existentes para exibir XP e badges.
8. **Novo schema `packages/shared/src/schemas/parent.schema.ts`** com `profileSummarySchema` (usado tanto para a resposta de `GET /profiles` quanto para o campo `profile` da jornada) e `journeyResponseSchema`, seguindo o padrão de `gamification.schema.ts`.
