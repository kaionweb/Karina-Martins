### Data Models

[Source: docs/architecture.md#Show / Track / Lesson]

Formato conceitual definido na arquitetura (TypeScript, a ser traduzido para a sintaxe Prisma seguindo o estilo já usado em `User`/`Profile`):

```typescript
export interface Show {
  id: string;
  title: string;
  synopsis: string; // conteúdo original, nunca copiado de terceiros
  thumbnailKey: string; // referência a asset do design system, não upload
  createdAt: string;
}

export interface Track {
  id: string;
  showId: string;
  title: string;
  order: number;
}

export interface Lesson {
  id: string;
  trackId: string;
  title: string;
  order: number;
  contentBody: string; // conteúdo original
  createdAt: string;
}
```

**Relationships:** `Show` 1:N `Track` 1:N `Lesson`. [Source: docs/architecture.md#Show / Track / Lesson]

Schema SQL de referência (autoritativo para a camada de banco MySQL/TiDB — a migração via `prisma db push` deve produzir um resultado equivalente a isto):

```sql
CREATE TABLE Show (
  id           VARCHAR(191) PRIMARY KEY,
  title        VARCHAR(191) NOT NULL,
  synopsis     TEXT NOT NULL,
  thumbnailKey VARCHAR(191) NOT NULL,
  createdAt    DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
);

CREATE TABLE Track (
  id      VARCHAR(191) PRIMARY KEY,
  showId  VARCHAR(191) NOT NULL,
  title   VARCHAR(191) NOT NULL,
  `order` INT NOT NULL,
  FOREIGN KEY (showId) REFERENCES Show(id) ON DELETE CASCADE,
  INDEX idx_track_show (showId)
);

CREATE TABLE Lesson (
  id          VARCHAR(191) PRIMARY KEY,
  trackId     VARCHAR(191) NOT NULL,
  title       VARCHAR(191) NOT NULL,
  `order`     INT NOT NULL,
  contentBody TEXT NOT NULL,
  createdAt   DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  FOREIGN KEY (trackId) REFERENCES Track(id) ON DELETE CASCADE,
  INDEX idx_lesson_track (trackId)
);
```

[Source: docs/architecture.md#Database Schema]

**Convenções já estabelecidas no schema atual** (seguir, não inventar novas): `id String @id @default(cuid())` (mesmo padrão de `User`/`Profile`, não UUID); `DateTime @default(now())` para `createdAt`; índice explícito na FK (`@@index`), como já feito em `Profile.userId`. Investigação direta (rodando o `.exe` via PowerShell) revelou a causa real: **Windows Smart App Control** está bloqueando o binário — "Uma política de Controle de Aplicativo bloqueou este arquivo". Confirmado via Event Viewer (`Microsoft-Windows-CodeIntegrity/Operational`, evento 3077): "Code Integrity determined that a process (powershell.exe) attempted to load ...schema-engine-windows.exe that did not meet the Enterprise signing level requirements". Registro de política (`HKLM:\SYSTEM\CurrentControlSet\Control\CI\Policy\VerifiedAndReputablePolicyState`) = `1` (**Avaliação** — ainda reversível via Configurações do Windows, sem precisar reinstalar o Windows). Diferente do bloqueio transitório da Story 1.1 (que era o `query_engine-windows.dll.node` e resolveu sozinho no retry) — este persistiu em múltiplas tentativas (via `npx prisma db push`, via execução direta do `.exe`, com `Unblock-File`). Bloqueado até o usuário decidir como prosseguir. **Resolvido:** usuário desativou o Smart App Control via Configurações do Windows (`VerifiedAndReputablePolicyState` 1 → 0); `prisma db push` executado com sucesso em seguida ("Your database is now in sync with your Prisma schema. Done in 3.16s"). Nota para stories futuras: se o bloqueio recorrer, o Smart App Control pode ter sido reativado.
