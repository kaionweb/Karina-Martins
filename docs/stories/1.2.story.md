## Story

**As a** responsável,
**I want** criar uma conta e fazer login,
**so that** acessar a plataforma com segurança mesmo com web e API em domínios diferentes.

## Acceptance Criteria

1. Endpoint de registro cria conta ADULT com senha (hash) e endpoint de login retorna access token JWT (expiração 15 min)
2. Refresh token é emitido como cookie httpOnly, `SameSite=None; Secure`
3. Toda lógica de auth do front está isolada em um service (`lib/auth`) conforme regra do domínio
4. Entradas validadas via zod (schemas em `packages/shared`)

[Source: architecture.md#API Specification]


### Technical Decision: Password Hashing Library

A `architecture.md` deixou essa escolha explicitamente em aberto ("hash com bcrypt/argon2 — a definir no story de implementação"). **Decisão desta story: usar `bcryptjs`** (implementação pura em JavaScript, sem binding nativo/compilação).

**Racional:** nesta mesma sessão de desenvolvimento, o binário nativo do Prisma (`query_engine-windows.dll.node`) foi temporariamente bloqueado por uma política de Controle de Aplicativo do Windows no ambiente de dev local (ver `docs/stories/1.1.story.md#Debug Log References`). O pacote `bcrypt` tradicional depende de compilação nativa (node-gyp) e correria risco similar; `bcryptjs` evita essa classe de problema inteiramente, ao custo de ser um pouco mais lento (irrelevante no volume de uma demo).

### Technical Decision: Refresh Token — Stateless (sem tabela no banco)

A `architecture.md` não define uma tabela de refresh tokens no Database Schema. Para não inventar uma tabela nova fora do que já foi arquitetado (Article IV — No Invention), o refresh token nesta story é um **JWT assinado com `JWT_REFRESH_SECRET`** (stateless), não uma linha em banco. Consequência aceita: `POST /auth/logout` apenas limpa o cookie no cliente — não há revogação server-side nesta story (um refresh token já emitido continua tecnicamente válido até expirar, mesmo após logout). Isso é uma limitação conhecida, aceitável para o escopo de demo; se precisar de revogação real, isso deve virar uma story própria no futuro (não inventar aqui).
