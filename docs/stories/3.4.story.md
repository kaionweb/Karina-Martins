## Scope Note (decisões registradas nesta preparação)

1. **Regra de concessão concreta (decisão de produto mínima — a AC só dá exemplos, "ex: baseada em XpEvents ou streak", não uma regra específica):** para demonstrar as duas bases citadas pela própria AC sem inventar um catálogo grande de conquistas (fora de escopo, nenhuma AC pede isso), esta story implementa **2 badges**:
   - `FIRST_LESSON` ("Primeira Lição") — concedida na primeira vez que um perfil conclui **qualquer** lição (baseada em `XpEvent`/`LessonProgress`, já existentes desde as Stories 2.3/3.2).
   - `STREAK_3` ("Sequência de 3 dias") — concedida quando `currentStreak` de um perfil atinge `3` (baseada em streak, Story 3.3).
   Mais badges/regras ficam para quem precisar delas explicitamente (não inventado aqui).
2. **Concessão é reativa, não um endpoint/cron novo.** A checagem acontece dentro dos fluxos que já existem e já alteram o estado relevante: `LessonsService.completeLesson` (depois de conceder XP, checa se é a 1ª conclusão) e `GamificationService.updateStreaks` (depois de calcular o novo `currentStreak`, checa se atingiu 3). Evita inventar um endpoint de "avaliação de badges" que nenhuma AC pede — mesmo raciocínio já usado para não conceder `STREAK_BONUS` na Story 3.3.
3. **Os 2 registros de `Badge` são garantidos via `upsert` por `code`** (chave única), executado no ponto de concessão, em vez de depender de um script de seed separado rodar antes. Isso mantém a story autocontida — não depende de ordem de execução com `packages/database/seed.ts` (que, pela Scope Note da Story 2.4, é escopo só de catálogo, badges ficam para a Story 5.3 "seed completo" — mas os badges *em si*, como conquistas reais do sistema, precisam existir desde já, não só no seed de demonstração).
4. **`iconKey` segue o mesmo padrão já estabelecido para `thumbnailKey`** (Story 2.1/2.2) — identificador string opaco, renderizado como bloco tipográfico/emoji, nunca um upload ou URL de imagem de terceiros (mesma regra de domínio do `CLAUDE.md`, agora aplicada a badges por analogia, já que a arquitetura usa a mesma forma de campo).
5. **"UI exibe badges conquistadas no perfil" (AC2) não tem uma página de destino pronta.** `/home` está listada em `docs/architecture.md#Route Organization` mas **nenhuma story construiu essa página ainda** (nem `/select-profile`, nem `/login` — só `/catalog` e `/lesson/[lessonId]` existem, das Stories 2.2/2.3). Esta story cria uma versão **mínima** de `/home` contendo só o grid de badges — não um dashboard completo (XP/streak ali também não foi pedido por nenhuma AC desta story). Mesma limitação de autenticação já registrada nas Stories 2.2/2.3/3.2 (Client Component, não navegável ponta-a-ponta por um usuário real sem tela de login).

### Data Models

[Source: docs/architecture.md#Badge / ProfileBadge]

```typescript
export interface Badge {
  id: string;
  code: string;
  title: string;
  description: string;
  iconKey: string;
}

export interface ProfileBadge {
  id: string;
  profileId: string;
  badgeId: string;
  awardedAt: string;
}
```

**Relationships:** N:N entre `Profile` e `Badge` via `ProfileBadge`. [Source: docs/architecture.md#Badge / ProfileBadge]

SQL de referência: [Source: docs/architecture.md#Database Schema]

```sql
CREATE TABLE Badge (
  id          VARCHAR(191) PRIMARY KEY,
  code        VARCHAR(60) NOT NULL UNIQUE,
  title       VARCHAR(191) NOT NULL,
  description VARCHAR(255) NOT NULL,
  iconKey     VARCHAR(191) NOT NULL
);

CREATE TABLE ProfileBadge (
  id         VARCHAR(191) PRIMARY KEY,
  profileId  VARCHAR(191) NOT NULL,
  badgeId    VARCHAR(191) NOT NULL,
  awardedAt  DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  UNIQUE KEY uq_profile_badge (profileId, badgeId),
  FOREIGN KEY (profileId) REFERENCES Profile(id) ON DELETE CASCADE,
  FOREIGN KEY (badgeId) REFERENCES Badge(id) ON DELETE CASCADE
);
```

### Debug Log References

- **`/home` aparece como `○ (Static)` no build, não `ƒ (Dynamic)` — não é uma repetição do ARCH-001 (Story 2.2).** `/home` é uma rota sem segmento dinâmico, então o Next.js consegue pré-renderizar a página inteira em build-time; como é um Client Component (`"use client"`) com fetch só dentro de `useEffect` (nunca no corpo do componente), nenhuma chamada de rede acontece durante o build — o HTML estático é só o estado inicial de "Carregando...", e os badges são buscados no browser após a hidratação. `/lesson/[lessonId]` continua `ƒ Dynamic` só por ter segmento de rota dinâmico (`[lessonId]`), não por causa de fetch. Build confirmado limpo.
- **Achado real de infraestrutura de teste (corrigido):** `packages/database/jest.config.js` nunca tinha recebido o ajuste de `testTimeout` que `apps/api/jest.config.js` recebeu na Story 2.3. O teste de seed (Story 2.4) usa `execSync` para rodar `tsx seed.ts` de verdade (processo novo + conexão real ao TiDB), que ocasionalmente passa do timeout padrão de 5s do Jest sob carga — apareceu pela primeira vez rodando a suíte completa desta story. Corrigido com `testTimeout: 15000`, mesmo padrão já usado em `apps/api`.
- Mesmo lock de arquivo do Windows no engine do Prisma já visto em stories anteriores (processo `node` órfão do `execSync` do teste de seed segurando a DLL) — resolvido encerrando processos `node` órfãos antes do build.
