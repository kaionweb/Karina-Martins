## Scope Note (decisões registradas nesta preparação)

Esta é a **primeira story do projeto que toca `apps/web` além do scaffold da Fase 0** (que só criou `layout.tsx`/`page.tsx`/tokens de tema — nenhuma tela real, nenhum cliente de API, nenhum componente shadcn/ui gerado, nenhuma infra de teste de frontend). Por isso o escopo desta story é maior que o das stories anteriores do Epic 1, mesmo com apenas 2 ACs:

1. **Sem rota protegida ainda:** o padrão `(app)/layout.tsx` com `getSessionFromCookie()` + redirect (`docs/architecture.md#Protected Route Pattern`) é conceitual — essa função não existe em código nenhum, e nenhuma tela de login/seleção de perfil foi construída ainda (mesma decisão de escopo já registrada na Story 1.4: "tela de seleção de perfil ficou para uma story futura de UI"). Como `GET /catalog/shows` é explicitamente público (`security: []` na especificação OpenAPI), esta story **não** constrói o shell protegido `(app)/` — a página fica em `apps/web/src/app/catalog/page.tsx`, sem gate de sessão. Proteger a rota fica para quando a tela de login/seleção de perfil for construída.
2. **`thumbnailKey` não tem mapeamento visual definido em nenhum documento-fonte** — a arquitetura só diz "referência a asset do design system, não upload" (`docs/architecture.md#Show / Track / Lesson`) e o `CLAUDE.md` só diz "cards tipográficos com paleta temática". Não existe lookup table, paleta por show, nem componente de referência. Esta story renderiza o card com um bloco tipográfico simples (cor de fundo do tema + título do show) — original, sem qualquer asset de imagem — e trata `thumbnailKey` como um identificador opaco armazenado, não como algo já mapeado a um visual específico (ficaria para uma story futura de design system, se o cliente pedir variação visual por show).
3. **Vitest + RTL (`docs/architecture.md#Frontend Testing`) ainda não está instalado em `apps/web`** — esta story faz essa instalação inicial, mesmo padrão do que a Story 1.1 fez ao adicionar Jest pela primeira vez a `packages/database`.
4. **`lib/utils.ts` (helper `cn()`) não existe ainda**, embora já seja referenciado por `apps/web/components.json` (`aliases.utils: "@/lib/utils"`) — criado nesta story como base para qualquer componente shadcn/ui futuro.

### Debug Log References

**Achado crítico fora do escopo original desta story, corrigido com aprovação explícita do usuário:** ao tentar verificar a UI no navegador (rodando a API de verdade, não só via testes Jest), descobri que `apps/api` **nunca tinha sido executável fora dos testes** desde a Story 1.2, por dois problemas pré-existentes e independentes:

1. **`packages/shared` e `packages/database` apontavam `main`/`types` para `.ts` cru** (`src/index.ts`), nunca compilado. Isso sempre funcionou nos testes (Jest/ts-jest resolve `.ts` via symlink do pnpm sem problema), mas quebra ao rodar `node dist/main.js` de verdade: o Node 24 tem suporte nativo a TypeScript (só faz *strip* de tipos, sem melhorar resolução de módulos), e ao carregar um `.ts` com sintaxe ESM (`export * from ...`) sem extensão de arquivo nos imports relativos, o resolvedor ESM nativo do Node falha com `ERR_MODULE_NOT_FOUND`. Isso afetaria o deploy real (Render/Koyeb rodam exatamente `node dist/main.js`). **Corrigido:** dei a ambos os pacotes um build real (`tsc` compilando para CommonJS em `dist/`), e `main`/`types` agora apontam para lá — mesmo padrão que `apps/api`/`apps/web` já usam. `packages/database` também ganhou um script `typecheck` que nunca existiu.
2. **`apps/api/src/main.ts` nunca carregava variáveis de ambiente** — só os testes carregavam `.env` (via `dotenv/config` no `jest.config.js`). Ao rodar o app de verdade, `process.env.GOOGLE_CLIENT_ID` etc. vinham `undefined`, derrubando o bootstrap (`GoogleStrategy` do Passport lança erro se `clientID` estiver ausente). Isso **não afetaria o deploy real** (Render/Koyeba injetam env vars diretamente no processo, sem precisar de `.env`), mas impedia qualquer verificação local fora dos testes. **Corrigido:** `import "dotenv/config"` como primeira linha de `main.ts` (`dotenv` movido de devDependencies para dependencies, já que agora é usado em runtime, não só em teste). `dotenv.config()` não sobrescreve env vars já setadas nem falha se `.env` não existir — seguro em produção.

Ambos os problemas eram pré-existentes (desde a Story 1.2), não introduzidos por esta story — só nunca tinham sido descobertos porque nenhuma story anterior rodou a API fora do Jest. Usuário aprovou investigar e corrigir agora (em vez de só documentar como dívida técnica) via pergunta explícita.

Depois da correção, verifiquei a UI de ponta a ponta num navegador real: `apps/api` rodando via `node dist/main.js`, `apps/web` via `next dev`, com 2 shows de demonstração temporários (criados e removidos só para o teste visual, não fazem parte do File List). Confirmado: cards renderizam com título/sinopse, thumbnail tipográfico (bloco colorido + inicial), tema claro e escuro corretos (via `[data-theme]`), sem erros no console do navegador.
