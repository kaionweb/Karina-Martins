## Story

**As a** responsável,
**I want** que o sistema saiba qual perfil da minha conta está ativo em cada requisição,
**so that** o conteúdo e as permissões sejam corretos para quem está de fato interagindo, e que essa informação sobreviva às chamadas seguintes sem eu precisar reenviar credenciais.

## Acceptance Criteria

1. `GET /profiles` retorna os perfis da conta do usuário autenticado
2. `POST /profiles/:id/select` valida que o perfil pertence à conta autenticada e reemite o access token com o perfil ativo embutido (`profileId`)
3. Chamadas subsequentes autenticadas com o novo token carregam o perfil ativo (verificável via um guard reutilizável)
4. Um perfil `CHILD` ativo não consegue listar os demais perfis da conta (nem ver seus dados)

### Technical Decision: "Sessão ativa" é o próprio JWT (sem estado no servidor)

Consistente com NFR1 (API sem estado em memória entre requests) e com o padrão já estabelecido na Story 1.2 (refresh token stateless): "selecionar um perfil" não grava nada em banco nem em memória do servidor — apenas **reemite o access token** com o claim `profileId` adicionado. O cliente troca o token antigo pelo novo (via `lib/auth`) e passa a mandar esse token em todas as chamadas seguintes. Isso evita inventar uma tabela de "sessão ativa" que não está na arquitetura.

### Debug Log References

- `tsc` falhou inicialmente em `jwt.util.ts`: `expiresIn: string` não é atribuível ao tipo esperado por `jsonwebtoken@9` (`SignOptions["expiresIn"]`, um tipo mais restrito que `string` genérico). Corrigido tipando o parâmetro como `jwt.SignOptions["expiresIn"]` em vez de `string`.
- Ajustei o código de sucesso de `POST /profiles/:id/select` de 201 (padrão do Nest para POST) para 200 explícito, por consistência com os outros endpoints que emitem token (`/auth/login`, `/auth/refresh`) — nenhum deles "cria um recurso", todos emitem um token.

### Completion Notes List

- Refatoração da Story 1.2 concluída como planejado: `AuthService` não assina mais JWT diretamente, usa `signAccessToken`/`verifyAccessToken` de `common/auth/jwt.util.ts`, agora compartilhado com `ProfilesService`.
- `GET /profiles` e `POST /profiles/:id/select` são os primeiros endpoints protegidos por `JwtAuthGuard` do projeto — guard testado indiretamente pelos casos 401 dos testes.
- Nenhuma tela criada (decisão de escopo já registrada no topo da story) — apenas o helper `selectProfile()` no `lib/auth`, sem UI que o chame ainda.
- AC3 ("chamadas subsequentes carregam o perfil ativo") foi verificado via teste: token pós-seleção ADULT continua funcionando normalmente em `GET /profiles`, e token pós-seleção CHILD é rejeitado (403) — prova que o `profileId` do token realmente é o que determina o comportamento, não apenas que o endpoint aceita o token.
- **Pós-QA (SEC-002, gate FAIL):** a primeira versão de `selectProfile` só validava se o perfil-alvo pertencia à conta, sem checar se o perfil *ativo* do chamador tinha permissão para trocar — um token CHILD conseguia se autopromover a ADULT chamando `/select` com o ID do perfil ADULT (que ele já conhecia de um `GET /profiles` anterior). Corrigido: `selectProfile` agora recebe o payload completo (`AccessTokenPayload`, não só `sub`) e bloqueia qualquer troca quando o perfil ativo é CHILD e o alvo é diferente dele mesmo. Perfil CHILD pode "reselecionar" a si mesmo (no-op, sem risco). 3 testes de regressão adicionados cobrindo exatamente os cenários do achado.

## QA Results

### Review Date: 2026-07-29

### Reviewed By: Quinn (Test Architect)

**Requirements Traceability (Given-When-Then):**

- AC1 — Given token de login (sem `profileId`), When `GET /profiles`, Then lista os perfis da conta → **coberto**
- AC2 — Given perfil válido da própria conta, When `POST /profiles/:id/select`, Then novo access token com `profileId` → **coberto**
- AC3 — Given token pós-seleção, When usado em chamadas seguintes, Then o perfil ativo é respeitado → **parcialmente coberto**: comprovado para o caso ADULT→lista OK e CHILD→lista bloqueada, mas **não** para o caso que realmente importa de segurança (ver SEC-002)
- AC4 — Given perfil CHILD ativo, When `GET /profiles`, Then 403 → **coberto** — mas essa mesma proteção **não existe** no endpoint de seleção, criando um desvio (bypass) direto: a criança não pode *listar*, mas pode *virar ADULT* e então listar à vontade.

**Risk Assessment:** **Alto.** Este é exatamente o tipo de falha que o Risk-Based Testing deveria pegar antes de qualquer coisa: a superfície mais sensível do produto (fronteira CHILD/ADULT) tem um bypass completo e trivial de explorar (não exige conhecimento técnico avançado — só chamar um endpoint com um ID que o próprio cliente já recebeu).

**Test Architecture:** 16/16 testes passam, mas a suíte testa os caminhos "conforme o roteiro" (seleciona o que devia, na ordem esperada) e não tenta ativamente quebrar a fronteira de autorização — um teste adversarial (token CHILD tentando virar ADULT) teria pego isso antes do QA.

**NFR Validation:**

- Segurança: **FAIL** — ver SEC-002. Este é um achado que bloqueia a liberação (`high`, "should block release" pela própria escala de severidade do projeto).
- Demais aspectos (manutenibilidade, refatoração do JWT util) estão bons — a arquitetura de guard/service é a correta, só falta o dado certo (perfil ativo) chegar até a checagem de autorização.

**CodeRabbit:** Não executado (mesma limitação de ambiente).

**Findings:** 1 achado `high` (SEC-002 — bloqueante). Nenhum outro achado relevante identificado (o resto do código está consistente com o padrão das stories anteriores).
