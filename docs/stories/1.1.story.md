## Story

**As a** responsável,
**I want** que o sistema saiba distinguir minha conta de adulto dos perfis das crianças vinculadas a ela,
**so that** cada um tenha uma experiência e permissões apropriadas.

## Acceptance Criteria

1. Schema Prisma expande os models `User`/`Profile` existentes para suportar tipo de perfil (ADULT/CHILD) e vínculo a uma conta familiar
2. Perfil CHILD armazena apenas apelido e faixa etária (sem sobrenome, foto, data de nascimento)
3. `prisma validate` e `prisma db push` executam sem erro no schema atualizado

### Data Models

[Source: architecture.md#Data Models — User]

O schema Prisma **já existe** desde a Fase 0 em `packages/database/prisma/schema.prisma`:

```prisma
model User {
  id           String    @id @default(cuid())
  email        String    @unique
  passwordHash String
  profiles     Profile[]
  createdAt    DateTime  @default(now())
  updatedAt    DateTime  @updatedAt
}

enum ProfileType {
  ADULT
  CHILD
}

model Profile {
  id        String      @id @default(cuid())
  userId    String
  user      User        @relation(fields: [userId], references: [id], onDelete: Cascade)
  nickname  String
  type      ProfileType
  ageRange  String?
  createdAt DateTime    @default(now())

  @@index([userId])
}
```

**Importante:** este schema **já atende** literalmente aos ACs 1 e 2 (tipo de perfil ADULT/CHILD, vínculo via `userId`, e ausência de campos de sobrenome/foto/data de nascimento). O trabalho real desta story é **auditar e confirmar** essa aderência (Task 1), não inventar novos campos. [Source: architecture.md#Data Models]

Não confundir com o nome `Account` — a arquitetura (`docs/architecture.md`) usa o nome conceitual `User` para a conta de login, consistente com o model já implementado; não criar um model `Account` separado.

Campos que **não** pertencem a esta story (não implementar aqui): `googleId` em `User` (Story 1.3 — Login social), `currentStreak`/`longestStreak`/`lastActiveDate` em `Profile` (Epic 3 — Gamificação). [Source: architecture.md#Database Schema]

### Debug Log References

- Bloqueio de ambiente: `DATABASE_URL` não existia em lugar nenhum do projeto (o `.env` da raiz é do tooling do Synkra AIOX, não da aplicação). Resolvido com provisionamento de um cluster TiDB Serverless gratuito pelo usuário.
- Tentativa de usar Docker local (MySQL em container) falhou: Docker Desktop não iniciava — "Virtualization support not detected" (virtualização desabilitada na BIOS da máquina). Abandonado em favor do TiDB Serverless real.
- `mysql://.../sys` foi a connection string inicial fornecida — `sys` é o schema reservado do MySQL; `prisma db execute` bloqueou com erro `P3004` ("system database"). Criado um banco dedicado `kaionweb` via `prisma db execute` conectado ao banco `test` (default do TiDB Serverless), e `DATABASE_URL` final apontado para `kaionweb`.
- Uma primeira tentativa de rodar `$executeRawUnsafe` via `@prisma/client` falhou com erro do Windows ("Uma política de Controle de Aplicativo bloqueou este arquivo" ao carregar `query_engine-windows.dll.node`); na segunda tentativa (segundos depois) funcionou normalmente — parece ter sido uma verificação de segurança de primeira execução do Windows, não um bloqueio permanente. Não impactou o resultado final.
