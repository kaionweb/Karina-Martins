## Scope Note (decisões registradas nesta preparação)

1. **Story fora do PRD original (`docs/prd.md`), solicitada diretamente pelo usuário após o PRD estar 100% completo (Epics 1-5, todas as 19 stories Done).** Numerada como Epic 6 ("extensão pós-MVP"), não altera nem reabre nenhuma story existente. AC própria (não copiada do PRD), autorada nesta preparação a partir do pedido literal do usuário ("priorizar login e chat da IA").
2. **`lib/auth` (Story 1.2) já implementa `register`/`login`/`logout`/`getAccessToken`/`selectProfile`** — toda a integração com a API já existe e funciona (token em memória, refresh automático via cookie httpOnly). O trabalho desta story é **só a UI** (páginas + navegação), reaproveitando essas funções sem alteração.
3. **`useProfileStore` (Zustand) é criado agora** — já estava previsto em `docs/architecture.md#State Structure` desde a Fase 1, mas nunca implementado (só `useXpToastStore`, Story 3.2, existe hoje). Guarda o perfil ativo (objeto completo retornado por `GET /profiles`, não só o ID) em memória — mesmo padrão de "sem persistência em localStorage" já usado para o access token (Story 1.2, decisão de segurança).
4. **Limitação arquitetural conhecida (Story 3.2, não corrigida aqui): o refresh token não carrega `profileId`.** Isso significa que, ao recarregar a página (ou após o access token expirar e ser renovado via refresh), o perfil ativo é perdido — o usuário precisa reselecionar. Esta story não resolve essa limitação (mudaria a assinatura do refresh token, fora do escopo de uma story de UI); em vez disso, a UI trata isso graciosamente: qualquer página protegida que exija um perfil ativo e não o encontre no `useProfileStore` redireciona para `/select-profile`, sem crashar.
5. **Guard de rota via hook client-side (`useAuthGuard`), não via Server Component com cookie** — mesma decisão arquitetural já tomada nas Stories 2.3/3.2/3.4/5.1 (evita a classe de bug ARCH-001 de fetch em build-time; token só existe no client, em memória). O hook redireciona para `/login` se não houver token, e opcionalmente para `/select-profile` se a página exigir perfil ativo.
6. **Todas as páginas protegidas existentes (`/home`, `/catalog`, `/catalog/[showId]`, `/lesson/[lessonId]`, `/dashboard`, `/dashboard/transcripts/[profileId]`) passam a usar `useAuthGuard`** — hoje nenhuma delas redireciona para login; só falham silenciosamente com uma mensagem de erro genérica se a chamada à API retornar 401. Mudança mínima (uma linha por página), sem alterar a lógica de fetch de dados já existente.
7. **`/register` não faz login automático** — `AuthService.register` (Story 1.2) só cria a conta, não retorna tokens (`return { id, email }`, sem `accessToken`). A página de registro redireciona para `/login` com uma mensagem de sucesso após criar a conta — não é uma limitação desta story, é o comportamento real já existente do backend.
8. **Header mínimo (`AppHeader`) criado para todas as páginas protegidas** — mostra o apelido do perfil ativo e um botão "Sair" (chama `logout()` + limpa `useProfileStore` + redireciona para `/login`). Nenhuma página protegida tinha qualquer navegação ou forma de logout até agora.

## Story

**As a** responsável,
**I want** fazer login e escolher qual perfil está usando a plataforma pela interface,
**so that** acessar o app sem precisar injetar token manualmente no console do navegador.

## Acceptance Criteria

1. Tela `/login` permite entrar com email/senha; em caso de sucesso, redireciona para `/select-profile`
2. Tela `/register` permite criar uma conta nova; em caso de sucesso, redireciona para `/login`
3. Tela `/select-profile` lista os perfis da conta autenticada e, ao escolher um, ativa a sessão com esse perfil (`useProfileStore`) e redireciona para `/home`
4. Páginas protegidas redirecionam para `/login` quando não há token válido, e para `/select-profile` quando não há perfil ativo
5. Páginas protegidas exibem o apelido do perfil ativo e permitem logout

### Debug Log References

**Bug real encontrado e corrigido durante a implementação:** `useAuthGuard` inicialmente incluía o objeto `router` (retornado por `useRouter()`) no array de dependências do `useEffect`. Como o teste (e, em tese, qualquer implementação de `useRouter` que não memoize o objeto retornado) pode retornar uma referência nova a cada render, isso causava um loop de re-execução do efeito. Corrigido removendo `router` das dependências — as funções `router.push`/`router.replace` do Next.js são estáveis entre renders, não precisam entrar no array (comentário explicativo deixado no código). Encontrado pelos próprios testes de `useAuthGuard`, que vazavam chamadas de redirecionamento entre `it` blocks antes da correção.

**Bug de build corrigido:** `useSearchParams()` em `/login` exigia um `Suspense` boundary (`next build` falhava com "should be wrapped in a suspense boundary"). Corrigido extraindo o conteúdo da página para um componente `LoginForm` interno, envolvido em `<Suspense>` no export default.
