## Scope Note (decisões registradas nesta preparação)

1. **Esta story fecha duas dívidas explicitamente deixadas por stories anteriores:** `POST /lessons/{id}/complete` foi adiado da Story 2.3 de propósito ("é a Story 3.2... gera XpEvent"), e `GET /gamification/xp` foi adiado da Story 3.1 pelo mesmo motivo. As duas pertencem à mesma story porque a UI desta story (AC2) depende de ambas ao mesmo tempo (concluir a lição E mostrar o XP total atualizado).
2. **Idempotência de conclusão (decisão técnica, nenhuma AC especifica isso, mas é necessária para a AC1 fazer sentido):** `LessonProgress` tem `@@unique([profileId, lessonId])` desde a Story 2.3 — chamar `POST /lessons/{id}/complete` numa lição já concluída **não** cria um novo `XpEvent` nem duplica `LessonProgress` (evita XP infinito reconcluindo a mesma lição). O endpoint retorna sucesso (200) tanto na primeira conclusão quanto em conclusões repetidas, mas só a primeira efetivamente cria `LessonProgress`+`XpEvent`. `LessonProgress` e `XpEvent` são criados numa transação (`prisma.$transaction`) para nunca existir um sem o outro.
3. **Valor de XP por lição: `10`, uma constante fixa.** Nenhuma AC ou documento-fonte especifica um valor — não existe fórmula, curva de dificuldade nem diferenciação por lição em nenhum lugar do PRD/arquitetura. `10` é um valor razoável de placeholder para a demo, documentado como constante nomeada (`LESSON_COMPLETION_XP`) para ser fácil de ajustar depois; não é uma decisão de produto definitiva.
4. **`zustand` é instalado pela primeira vez** (já é dependência declarada na Tech Stack da arquitetura, mas nunca foi de fato adicionada ao `package.json` do `apps/web` nem usada). Esta story cria o primeiro store (`stores/useXpToastStore.ts`), conforme `docs/architecture.md#State Management Patterns`: "toasts de XP via Zustand, mínimo e local ao app shell".
5. **`XpBar` segue o exemplo já dado literalmente na arquitetura** (`docs/architecture.md#Component Template`) — puramente apresentacional, recebe `currentXp` via prop, não busca dados sozinho.
6. **Mesma decisão de Client Component das Stories 2.2/2.3:** a UI desta story vive na página `/lesson/[lessonId]` já existente (Client Component desde a Story 2.3, por causa da ausência de tela de login) — `docs/architecture.md#State Management Patterns` sugere Server Component para "estado de servidor (XP)", mas isso não é possível aqui pela mesma razão já registrada nas duas stories anteriores (token só existe em memória no browser). Mantém consistência com o resto do app em vez de introduzir um padrão novo isolado.

## Story

**so that** ver meu progresso crescer.

### Debug Log References

**Achado real, fora do escopo desta story, encontrado durante a verificação visual:** o refresh token (JWT stateless desde a Story 1.2) só codifica `{ sub: userId }` — nunca `profileId`. Isso significa que, hoje, **nenhuma página do app consegue manter um token com perfil ativo depois de um reload/refresh silencioso**, porque não existe UI de seleção de perfil (só backend, desde a Story 1.4) para popular isso em memória originalmente, e o refresh nunca re-deriva/preserva essa informação. A Story 2.3 mascarou o sintoma (endpoints toleravam `profileId` ausente, mostrando progresso vazio sem erro). Esta story tem endpoints mais estritos (`POST /lessons/:id/complete`, `GET /gamification/xp` — ambos exigem perfil ativo, lançando `ForbiddenException` se ausente), o que tornou a lacuna visível: ao navegar para `/lesson/[lessonId]` numa aba nova (mesmo após autenticar via console, já que não há tela de login), a página cai no estado de erro (`"Não foi possível carregar a lição."`) em vez de mostrar o conteúdo — sem crash, sem exceção não tratada, comportamento gracioso confirmado. **Isso não é um bug desta story** — é uma lacuna pré-existente da Story 1.2 (design do refresh token), só ficou visível agora porque é a primeira story com um endpoint que exige perfil de forma estrita. Fica registrado para quando a story de login/seleção de perfil UI for construída (vai precisar resolver isso, provavelmente incluindo `profileId` no refresh token ou re-derivando o "último perfil selecionado" no backend).

Dado esse achado, a verificação visual desta story ficou parcial: **confirmado ao vivo** — a API real com `POST /lessons/:id/complete`/`GET /gamification/xp` funcionando corretamente contra o TiDB (via testes de integração, que simulam o fluxo completo com token de perfil real obtido via `/profiles/:id/select`); o build de produção mantém `/lesson/[lessonId]` como `ƒ Dynamic`; a página degrada graciosamente sem token de perfil válido. **Não confirmado ao vivo** — o clique no botão "Concluir lição" disparando a animação do toast, porque isso exigiria um token de perfil ativo dentro da própria sessão do navegador, que hoje só é alcançável via chamadas diretas (curl/console), nunca pela UI real (mesma limitação já registrada nas Stories 2.2/2.3/3.2 Scope Notes). Usuário decidiu aceitar a cobertura atual (testes de integração + teste de componente + revisão de código) como suficiente para fechar esta story.
