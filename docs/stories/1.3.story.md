## Scope Note (decisão registrada nesta story, seguindo o precedente da Story 1.4)

Não existe nenhuma tela de login/cadastro em `apps/web` ainda (apenas o placeholder de `apps/web/src/app/page.tsx` desde a Fase 0) — nem para email/senha (Story 1.2), nem para seleção de perfil (Story 1.4). Seguindo o mesmo recorte já aceito na Story 1.4, **esta story implementa apenas o fluxo OAuth no backend** (`apps/api`): iniciar o redirect, processar o callback do Google, criar/associar o `User` e emitir os mesmos tokens da Story 1.2. O callback redireciona o navegador de volta para `WEB_URL` (raiz) já com o cookie de refresh emitido; nenhuma alteração em `apps/web` é necessária, pois o mecanismo de refresh silencioso (`getAccessToken()` em `apps/web/src/lib/auth/index.ts`, da Story 1.2) já sabe trocar esse cookie por um access token quando qualquer página futura for carregada. O botão "Entrar com Google" em si fica para a futura story de UI de autenticação (ainda não criada no backlog).

## Story

**As a** responsável,
**I want** entrar com minha conta Google,
**so that** não precisar criar outra senha.

2. Conta criada via Google segue as mesmas regras de emissão de JWT/refresh cookie da Story 1.2

### Review Date: 2026-07-29

### Reviewed By: Quinn (Test Architect)

**Requirements Traceability (Given-When-Then):**

- AC1 — Given um perfil Google novo, When `AuthService.loginWithGoogle` é chamado, Then cria `User`(`passwordHash: null`)+`Profile ADULT`; Given um perfil Google cujo email coincide com uma conta já cadastrada por senha (e `emailVerified: true`), When chamado, Then associa `googleId` sem apagar `passwordHash` → **coberto** por 3 testes (novo usuário, reconhecimento por `googleId` recorrente, associação por email)
- AC2 — Given uma conta criada/associada via Google, When os tokens são emitidos, Then usa o mesmo `issueTokens`/mesmas opções de cookie da Story 1.2 → **coberto** por inspeção de código (reaproveita `issueTokens` sem duplicar) + teste de emissão de refresh token
- Ambas as ACs são satisfeitas na camada de **lógica de negócio** (`AuthService.loginWithGoogle`). Porém nenhum teste exercita os endpoints HTTP reais (`GET /auth/google`, `GET /auth/google/callback`) através do `AuthGuard("google")`/Strategy do Passport de verdade — ver TEST-002.

**Test Architecture:**

- 27/27 testes passam (16 de regressão + 11 novos), reexecutados de forma independente nesta revisão, não apenas confiando no relato do `@dev`.
- A suíte nova testa exatamente os caminhos que a `AuthService` decide (create/link/reject), incluindo o cenário de hardening (`emailVerified: false` bloqueia associação) — isso é bom e mostra que o achado do `@po` na validação foi implementado corretamente.
- **Porém**, ao ler o código da `GoogleStrategy`/`AuthController` linha a linha (não apenas os testes), encontrei uma lacuna que nenhum teste poderia ter pego, porque fica inteiramente na camada de protocolo OAuth que os testes atuais não tocam (ver SEC-003). Este é exatamente o padrão que pegou o SEC-002 na Story 1.4: os testes "conforme o roteiro" passam, mas ninguém tentou quebrar a fronteira de confiança do protocolo.

**Risk Assessment:** **Alto.** Confirmei lendo o código-fonte de `passport-oauth2` instalado neste projeto (`node_modules/.pnpm/passport-oauth2@1.8.0/lib/state/null.js`) que o `NullStore` usado por padrão (nenhuma opção `state`/`store` foi passada em `GoogleStrategy`) sempre aceita qualquer callback sem validar o parâmetro `state` (`verify = (req, state, cb) => cb(null, true)`). Isso é a lacuna clássica de **login CSRF em OAuth2**: um atacante pode iniciar seu próprio fluxo com a própria conta Google, capturar a URL de callback com o `code`, e induzir a vítima a abri-la — o navegador da vítima completa o callback e recebe o cookie de refresh de uma conta que pertence ao atacante. A vítima passa a operar "logada" na conta do atacante sem perceber, podendo inserir dados sensíveis (perfil de criança, uso do chat de IA) que ficam visíveis ao atacante. Dado que este produto lida especificamente com dados de crianças (tema recorrente em todo o PRD/CLAUDE.md), considero isso equivalente em severidade ao SEC-002 da Story 1.4, mesmo satisfazendo as ACs literais.

**NFR Validation:**

- Segurança: **FAIL** — ver SEC-003. O hardening de `email_verified` (Task 5.1) está correto e bem testado, mas não cobre esse vetor diferente (CSRF de protocolo, não de dados). Também confirmado: nenhum vazamento de token via URL de redirect (`res.redirect(WEB_URL)` sem query string), nenhum open-redirect (destino fixo via env, não vindo de input do usuário).
- Manutenibilidade: boa — `loginWithGoogle` reaproveita `issueTokens` sem duplicação, segue o padrão de erro (`apiErrorBody`) já estabelecido.
