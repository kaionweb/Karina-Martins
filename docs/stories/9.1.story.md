## Scope Note (decisões registradas nesta preparação)

1. **Story fora do PRD original, Epic 9 (mesmo padrão dos Epics 6/7/8: sem documento de epic formal — decisões registradas na seção Scope Note de cada story, cerimônia de `*create-epic` não usada).** O usuário aprovou (fora do fluxo formal AIOX, via gate-first do `CLAUDE.md`) a integração de vídeos do YouTube como conteúdo de imersão, com gate técnico completo apresentado pelo `@aiox-master`. Esta story cobre a fundação de dados (schema Prisma) e a ingestão de conteúdo (sincronização periódica com a YouTube Data API v3) que sustentam o catálogo de vídeos (Story 9.2, listagem/filtros) e o player com gamificação (Story 9.3, detalhe/heartbeat/XP).
2. **Curadoria de playlists é manual, fora do escopo desta story.** O modelo `CuratedPlaylist` (`playlistId`, `channel`, `active`, `level`, `ageRange`, `skill`, `theme`) pressupõe que alguém insere as linhas iniciais diretamente no banco (script/seed manual) antes do primeiro sync — não existe UI/endpoint de administração de playlists em nenhuma story aprovada até aqui. O `YoutubeSyncService` **só processa `CuratedPlaylist` com `active: true`**; nunca descobre playlists novas sozinho.
3. **Cota da YouTube Data API v3: só `playlistItems.list` e `videos.list`, nunca `search.list`** (decisão explícita do gate aprovado — `search.list` custa 100 units contra 1 unit de `playlistItems.list`/`videos.list`). `videos.list` é chamado em lotes de até 50 ids por requisição (limite da própria API), minimizando o número de chamadas.
4. **Vídeo sumido/privado nunca é deletado, só `status: UNAVAILABLE`** — preserva o histórico de `VideoWatch`/`XpEvent` já emitidos para aquele vídeo (FK nunca quebra). A remoção da listagem pública (`GET /videos`, Story 9.2) é feita filtrando por `status: AVAILABLE`, não pela ausência do registro.
5. **`YOUTUBE_API_KEY` só existe em `apps/api`, nunca em `apps/web`** — mesmo padrão já usado para `ANTHROPIC_API_KEY` (`CLAUDE.md`, seção "IA (Anthropic API)": "SOMENTE a apps/api chama a Anthropic. ANTHROPIC_API_KEY nunca existe no web").
6. **`POST /internal/cron/videos-sync` reaproveita literalmente o padrão de `StreakCronController`** (Story 3.3, `apps/api/src/modules/gamification/streak-cron.controller.ts`): `CronSecretGuard`, `@HttpCode(200)`, autenticado por header `X-Cron-Secret` (env `CRON_SECRET`, já existente — reaproveitado, não é um novo secret). Chamado 1x/dia por cron externo (cron-job.org no ambiente de teste), mesmo modelo operacional do streak.
7. **`youtube.client.ts` é um wrapper fino e isolado do `fetch`** especificamente para permitir mock nos testes (unitário do `YoutubeSyncService` e integração do endpoint de cron) sem golpear a API real do YouTube.
8. **Novos modelos Prisma nesta story, dentro de uma story de feature (não uma story "modelo de dados" dedicada)** — mesmo padrão já usado na Story 4.5 (`AiSession`/`AiMessage` criados dentro da story de feature "Limite diário e auditoria de tokens", executor `dev`/quality_gate `architect`, não `data-engineer`/`dev`). As stories "modelo de dados" dedicadas (1.1, 2.1) usam `data-engineer`/`dev`; esta story segue o padrão de feature, pois o schema está indissociável da lógica de sincronização que o acompanha.

## Story

**As a** mantenedor da plataforma,
**I want** que o catálogo de vídeos curados seja sincronizado automaticamente com o YouTube todos os dias,
**so that** o conteúdo disponível para os perfis reflita o que está realmente publicado e acessível no YouTube, sem trabalho manual de atualização.

## Acceptance Criteria

1. `POST /internal/cron/videos-sync` (protegido por `CronSecretGuard`, header `X-Cron-Secret`) itera todas as `CuratedPlaylist` com `active: true`, busca os itens de cada playlist via `playlistItems.list` e os metadados via `videos.list` (lotes de até 50 ids), e faz upsert de `Video` (por `videoId`) vinculado à `CuratedPlaylist` correta
2. Vídeo que não é mais retornado pela playlist (removido/privado no YouTube) tem seu `status` atualizado para `UNAVAILABLE`; nenhum registro de `Video` é deletado
3. Requisição sem header `X-Cron-Secret`, ou com valor incorreto, retorna 401 e não dispara nenhuma chamada à YouTube API
4. Os modelos Prisma `CuratedPlaylist`, `Video`, `VideoWatch` (com os enums `PlaylistLevel`, `VideoSkill`, `VideoStatus`) e o novo valor `VIDEO_COMPLETED` em `XpEventSource` existem no schema, passam em `prisma validate` e o client gerado (`@ipp/database`) exporta os tipos correspondentes

### Data Models (schema aprovado no gate técnico, sem documento de arquitetura formal para o Epic 9 — ver Scope Note)

```prisma
enum PlaylistLevel { INICIANTE INTERMEDIARIO }
enum VideoSkill { VOCABULARIO LISTENING MUSICA }
enum VideoStatus { AVAILABLE UNAVAILABLE }

model CuratedPlaylist {
  id         String         @id @default(cuid())
  playlistId String         @unique
  channel    String
  active     Boolean        @default(true)
  level      PlaylistLevel
  ageRange   String
  skill      VideoSkill
  theme      String
  videos     Video[]
  createdAt  DateTime       @default(now())
}

model Video {
  id              String       @id @default(cuid())
  videoId         String       @unique
  playlistId      String
  playlist        CuratedPlaylist @relation(fields: [playlistId], references: [id], onDelete: Cascade)
  title           String
  channel         String
  durationSeconds Int
  thumbnailUrl    String
  status          VideoStatus  @default(AVAILABLE)
  syncedAt        DateTime     @default(now())
  watches         VideoWatch[]
}

model VideoWatch {
  id             String    @id @default(cuid())
  profileId      String
  profile        Profile   @relation(fields: [profileId], references: [id], onDelete: Cascade)
  videoId        String
  video          Video     @relation(fields: [videoId], references: [id], onDelete: Cascade)
  watchDate      DateTime  @db.Date
  watchedSeconds Int       @default(0)
  completedAt    DateTime?
  updatedAt      DateTime  @updatedAt

  @@unique([profileId, videoId, watchDate])
}
```

`Profile` ganha `videoWatches VideoWatch[]`. `XpEventSource` ganha `VIDEO_COMPLETED` como novo valor do enum existente (reaproveita o `model XpEvent` já existente — nunca uma tabela nova de XP).
