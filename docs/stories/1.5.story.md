## Story

**As a** mantenedor da plataforma,
**I want** que a API só aceite requisições da origin do front-end oficial,
**so that** reduzir risco de CSRF/CORS mal configurado.

## Acceptance Criteria

1. CORS da API restrito à origin de `WEB_URL` (nunca `"*"` com credentials)
2. `GET /health` responde 200 sem tocar o banco, para healthcheck da plataforma de deploy

### Technical Decision: fail-fast se `WEB_URL` não estiver configurado

Lendo o código-fonte da lib `cors` instalada (`node_modules/.pnpm/cors@2.8.5/lib/index.js`, usada internamente por `app.enableCors()` do NestJS), a função `configureOrigin` tem este comportamento:

```javascript
if (!options.origin || options.origin === '*') {
  // allow any origin
  headers.push([{ key: 'Access-Control-Allow-Origin', value: '*' }]);
}
```

Ou seja: se `process.env.WEB_URL` estiver `undefined` (env var não configurada — um erro de configuração de deploy plausível no Render/Koyeb), `app.enableCors({ origin: undefined, credentials: true })` faz a lib **silenciosamente degradar para `Access-Control-Allow-Origin: "*"`** — exatamente o que a AC1 desta story proíbe explicitamente ("nunca `*` com credentials"). Navegadores reais já rejeitam a combinação `*` + credentials do lado do cliente, então isso não é um vazamento direto de cookies, mas é: (a) uma falha de configuração que se torna invisível — a API "funciona" para requisições não-credenciadas de qualquer origin sem nenhum aviso; (b) exatamente o tipo de regressão silenciosa que esta story existe para prevenir. Por isso a Subtask 1.2 pede um erro explícito e alto (fail-fast) no bootstrap se `WEB_URL` faltar, em vez de deixar o comportamento padrão da lib mascarar o problema.
